# Datepicker candidate qualification contract

Only material-datepicker-v1 is writable. Existing canonical sources, runtime implementations/manifests, models, DB, compiler, catalog and reference bytes stay frozen. No sealed evaluation/qualification archives. This is a candidate admission, not promotion. Candidate target: five facts, one document, 104 facts/23 documents total, exact Formly6.3.12 Material only.

Source verification: retrieve K13/K18/K19 from pinned upstream commit 5f099fddea6426b46a453866adf0fede5be0bcd7, require full-file SHA256 equality to existing catalog; use existing material.md exact quotations. No new evidence/catalog changes. Record every material.md paragraph as proposed/existing support/excluded/pending without superseding old select decisions. Read only the source files, not source-linked evaluation evidence.

Five proposed claims: registration outside umbrella module; separate date adapter configuration; nested min/max/filter bindings; startView/touchUi/startAt bindings; dateInput/dateChange and month/year callback arguments. Limits: no claim of universal date parsing/serialization/timezone behavior, no event sequencing/model-commit guarantee, no complete app recipe or new major coverage.

Build safety: use existing schema2 compiler in an exclusive isolated directory. Preserve every row of eight knowledge tables, verify exact source offsets/hashes, foreign keys, runtime scope eligibility and counts. Candidate input copying cannot overwrite an existing file. Tests exercise lost applicability rows, wrong counts, allowed arms/tools, output overwrite refusal and failure accounting. Transport/server are copied from the accepted POC experimental harness (no runtime changes); copied code remains within this POC. New logic receives tests first.

Fixed qualification: cases.json contains 10 datepicker questions and five controls. Freeze all requests, plans, criteria, facts, harness and source receipts before build/run. Identical full-question caller plans for baseline and candidate isolate data effect, not planner quality. 3 repeats x 2 arms x 15 cases =90 lookup observations, batches of5. Same runtime factories under offline guard, no server models/network/subprocesses, no spawned agent CLI. The calling agent in this conversation reviews actual output, chooses discovery/fetch and writes supported answers. One answer per unique packet may be reused only after exact packet equality verification; report unique authored answers separately from repeated observations. Do not claim 90 independent generations.

Recovery: at most2 plan repairs preserving request, retain failures; discovery up to2 pages of16 and fetch up to2 requests of16 observed IDs only. Source oracle IDs in cases are scoring diagnostics, never used to fetch unseen IDs. Unsupported scope stops. No tuning during fixed run. Any failed attempt remains in reports.

Acceptance: >=14/15 usable candidate answers EACH repeat; every control usable; zero critical unsupported claims, operational failures or baseline-supported regressions. D10 is a boundary question: a qualified supported explanation of lack of universal guarantee passes; mere no-evidence on answerable D01-D09 is incomplete. C04 must stop at unsupported version; C05 must not deliver Material facts as Bootstrap guarantees. Controls C01-C03 must retain supported answers. Initial packet versus post-discovery support reported separately. Real answer semantics and citations audited independently; successful delivery alone is not a usable answer.

Independent reviews: max3 fresh instances total, initial prebuild mapping/plan and final outcome. Reviewer starts with neutral bootstrap and records preliminary findings before author explanation. No promotion or publishing in this task. End with measured results and recommendation.
