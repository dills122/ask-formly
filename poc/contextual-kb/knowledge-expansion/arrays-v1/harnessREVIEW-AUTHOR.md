# Arrays harness author explanation

The isolated arrays batch compares installed foundation6 (79 facts / 17 documents) with a proposed 85-fact / 19-document candidate. The count derives from six proposed facts across two new documents. No installed runtime, DB, authored inputs, catalog, compiler, models or sealed evaluation were modified by harness preparation. No candidate build or live generation was performed by the harness worker.

The harness reuses frozen validation-v1. Candidate builder changes are the expected counts; evaluator wording names this batch. Experiment, delivery verification, semantic assessment, fixed-denominator summary, paired-plan replay, schemas and grader instructions remain byte-identical to validation-v1. Accepted runtime classes are imported unchanged, with explicit checked read-only database selection. Both arms retain the same caller and lookup-only invocation approval settings; global settings and sandbox policy are unchanged.

The baseline state verifies 167 protected file pins and the installed database hash. Pins combine the current foundation6 manifest, packaging source manifest, canonical authored JSON, compiler Python and corpus files; both manifests themselves are pinned. Existing manifest hashes were verified before capture. The isolated builder retains exclusive output creation, candidate input hashes, source offset validation, foreign-key checks, all five accepted knowledge-table row subsets and runtime retrieval eligibility. It does not overwrite any existing candidate output.

Qualification comprises ten new arrays requests A01–A10 and the five unchanged validation-batch regression/gap controls E05, M03, Q20, Q21 and Q24. The new cases cover template/children and control/index behavior; add/remove coordination; exact markAsDirty defaults; falsy initialModel behavior; the conditional upstream default/insertion test; example alias/renderer registration; and the Bootstrap-to-Material boundary. Development requests are separate and excluded from scoring. Fact IDs are diagnostics; semantic equivalence and appropriate limitations govern grading.

The contract is fixed before execution: three repeats with seeds 1701/1702/1701, both arms receiving all 15 cases, at least 14/15 candidate answers usable in each repeat, every control passing, zero critical or delivery failures and zero regressions on baseline-supported cases. Missing/duplicate assessments remain failures with fixed denominators. All 90 live answers are assessed. The existing replay method takes 15 saved plans per repeat, from baseline/candidate/baseline respectively, and runs them against the opposite arm: 45 directional paired retrieval comparisons. These are packet diagnostics, not additional live answers and not a replay of all 90 distinct plans. The plan was clarified before freeze/results to match this established method.

Initial new-module tests failed before implementation. More significantly, the count tests then ran against the copied frozen builder and rejected 85/19 while exposing its old 79/17 constants (`test-output/tdd-count-red.txt`). Changing only those constants produced green. All 16 candidate-isolation, batch and evaluation tests pass (`test-output/tdd-final-green.txt`). These tests verify output isolation, digest drift rejection, no overwrite/redirection, exact count drift, lookup-only caller settings, per-repeat gates, baseline regressions, malformed/missing/duplicate assessments and fixed required cases. They do not establish live retrieval quality or execution of upstream Formly tests.

Parent owns review, freeze, isolated build, live execution, independent answer audit and the project maintenance check. Retain failures and receipts; do not tune or rerun the fixed qualification set into a pass. Independent review and preservation checks remain necessary even if the scripted evaluator reports qualified. Promotion remains separately authorized work.
